## T1 — a run that used a test hook is never ranked

**D2 — Acceptance criteria (derived).** (a) Any URL test hook in effect at a run's start (`seed`, `speed`, `boss`, `fps`, `crowd`, `elite`, `fusion`, `pickups`: every field `parseTestHooks` reads; no other Survival hook exists in `app/`) makes the run unrankable: no leaderboard form, no `startSurvivalRun` call. (b) The results say why in one line, naming the hooks. (c) The hooks behave as before. (d) A unit test shows a run with a hook marked unrankable and one without rankable. (e) An e2e test shows a seeded run's results with no leaderboard entry.

**D3 — "In effect", not "present".** A hook the URL names but cannot use (`?seed=0`, `?speed=1`, `?fps=0`) already "reads as no hook at all" (test-hooks.ts), so it does not count against the run either. Only a hook that changes something blocks ranking. `activeTestHooks` reuses `parseTestHooks`, so the bounds cannot drift apart. A unit test checks that it can name every field of `TestHooks`, so a hook added later without a name there fails.

**D4 — The seed and the frame counter now count too.** Before this task they were exempt, on the grounds that "a seed and the frame counter do not change the game". The plan names `?seed` and `?fps`. A seed lets a run be replayed until it is known, and is the easiest of them to share. The existing signed-out and signed-in leaderboard e2e tests used `?seed=7` only for repeatability, so they now run unseeded (they give up after 1.5 s, which no seed affects).

**D5 — The `survival` browser group now depends on the login setup.** The new test uses the demo user's session. `survival` was not in `LOGGED_IN` in `playwright.config.ts`, so a targeted run (`E2E_NO_CAT_DEPS=1`) reused whatever `playwright/.auth/demo-user.json` an earlier run left, signed with that run's throwaway `AUTH_SECRET`. That showed in this task as a `JWTSessionError` and a test that passed signed out. In a full run it worked only because `cat-attacks` (which depends on `setup`) ran first. The new test also opens `/dashboard` first and expects to stay there, so it cannot pass signed out. Changing `playwright.config.ts` makes the selector print `FULL` for this task's gate.

**D6 — What the server can and cannot check about a submitted run.** `recordSurvivalRun` (actions.ts) holds a run to: the signed-in player's own run, started by `startSurvivalRun`, finished once; a time no longer than its length, and no longer than the server's elapsed time since its start plus 2 s; at most 100 cats a second (+10); at most 60 finished runs an hour. It **cannot** see the URL, so it cannot tell whether a hook was used. The rule in this task is the client's, and stops an honest player posting a test run, not a cheater: Server Actions are public endpoints, so anyone signed in can call `startSurvivalRun`, wait, and call `recordSurvivalRun` with any time up to the real time elapsed and a plausible cat count, without playing. Nor can it check that the time was survived rather than idled. Stronger checks are proposed in Q3, not built (the plan says so).

## T3 — the results screen says what each weapon did

**D13 — Acceptance criteria (derived).** (a) For each weapon held during the run, evolved and fused ones included, the results show the homesickness it dealt and the cats it sent home, highest first; (b) as a list a screen reader reads sensibly (an `<ol>` named by its heading, one item per weapon, in words); (c) counted in the simulation (`arena.ts`), not the view; (d) unit tests on the counting; (e) an e2e test: a seeded run's results name the starting weapon with a non-zero count.

**D14 — How it is counted.** `arena.ts` names the weapon whose work is being done with `deal(id)` (first a `dealer` variable; since D16 `deal()` also works out the credited weapon and its counts once). Each phase that can hurt calls it: a weapon's own firing (`runWeapon`, a fused weapon's extra), each projectile and patch, the vacuum's burst, each sock, each swatted cat bowling. It is reset to none between phases, so a site that forgot to name its weapon counts nothing, and the every-weapon test fails. That was checked by removing one site: 25 tests failed. `hurt` credits that weapon with what the cat actually took (after immunity, elite and scorch factors). A cat sent home counts for the weapon that hurt it last. "Highest first" is by homesickness, then cats sent home. In co-op the list is the run's, both Keepers' together: the plan names one list, and the co-op results already show each Keeper's own weapons.

**D15 — Fused weapons.** A fused weapon goes on firing its two parents. Their work after the fusion counts for the fused weapon, which is what the player holds, and what they did before it stays theirs. So all three are listed. A weapon held but not yet fired is listed with 0. The listed weapons are those held at any point (starting, chosen, evolved into, fused into). The base a weapon evolved from stays listed with what it did before it evolved.

## E3 — a cap on what one account can create (exploration, security and quality)

**D33 — Why, and the numbers.** Every Server Action checks the session and validates its input; sign-up, login, password changes and leaderboard entries are rate-limited. But `createInvoice` and `createCustomer` had no bound. A signed-in caller (an action is a public endpoint) could create rows without end: an abuse of the database, and of the account's own pages. Every customer fills the invoice form's dropdown (`fetchCustomers` is unbounded), and past 10,000 invoices the CSV export refuses outright. A rate per hour would need a creation time the tables do not have (a migration, outside exploration), so the bound is a cap on the account's totals instead. It is checked in the `INSERT` itself, so the normal path is still one statement: at most 1,000 customers (`MAX_CUSTOMERS_PER_ACCOUNT`) and 10,000 invoices (`MAX_INVOICES_PER_ACCOUNT`, `EXPORT_LIMIT`'s number, so "export all" always fits). The numbers are far past any real use of the app, and changing them is one constant each (in `schemas.ts`: a `'use server'` file may export only async functions). Two parallel creates at the cap could each pass the count and end one over; that is accepted for a soft cap. When an invoice insert matches nothing, a second query tells "not your customer" (as before) from "the account is full" (a message naming the cap). The SQL itself runs in the browser tests that create customers and invoices; the unit tests cover both refusals and the parameters the insert gets.

**D34 — The reviewer's E3 finding: the cap's message was never shown.** Request changes, one Low. The invoice create form showed only field errors, never `state.message`, so an account at the invoice cap would click Create Invoice and see nothing. The same already happened to the generic database error. The form now has a message region (`aria-live="polite"`, as `customer-form.tsx` has) for a message that comes with no field error. A message that comes with field errors ("Missing Fields…") stays unshown, as before, since the fields say it. A jsdom test in `forms.test.tsx` submits at the cap and finds the message in that region, with no field blamed. The edit form has the same gap for its database error: noted, not changed, since no new refusal reaches it.

## E8 — a leaderboard name cannot stack marks into a tower (exploration, security and quality)

**D38 — The rule, and why three.** The leaderboard is the one page every visitor sees, and `LeaderboardName` took any number of combining marks (`\p{M}`): one letter and 19 marks fit the 20-character limit and draw a tower over the rows above and below (the "Zalgo" trick). A mark must now follow a letter, a digit or another mark, and four or more in a row are refused, with "A letter can carry at most three accents." Why three, not two: after NFC, Latin names need one or two, but some scripts stack three on a letter (Burmese ကိုး, "nine": ka with i, u and the visarga). Devanagari's vowel signs and virama pass, and are tested. The rule is in the schema the Server Action (`recordSurvivalRun`) and the form both use, so it holds on the server. Names already on the board are not touched. The tests write the marks as code points, so they can be read.
**Corrected after review (request changes, one Medium, one Low).** "Some scripts three" was wrong. Burmese medial consonants are marks too, and ကျော် (Kyaw), မျိုး (Myo) and မြို့ (Myo, a city), among the commonest parts of Burmese names, carry four, which the rule refused. Only non-spacing marks (Mn) pile up on one spot; spacing marks (Mc) move the text along. So the count is now of Mn in a row, four or more refused. Kyaw has one, Myo two, the city three, and all three are now tested to pass. The reviewer also found Devanagari, Tibetan, pointed Hebrew, Thai, Khmer and Bengali names within that. The tower ("a" and 19 acutes) is still refused. A mark with nothing under it now has its own message, "An accent must be on a letter.", in place of the three-accent one, which named a different problem.
Re-review: approve, one Low: enclosing marks (Me, e.g. U+0489) were not counted, so "a" with 19 of them passed. They are now counted with the non-spacing ones, with a test.

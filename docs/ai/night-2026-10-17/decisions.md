# Decisions

## Run

**D1 — Reading the plan's order.** The plan's order line reads "1, 2, 3, 4, 5, 6, checkpoint 1, 7, 8, checkpoint 2, then exploration", but its task list stops at 6; there is no task 7 or 8 to do, and inventing them would be scope the plan does not give. So: tasks 1–6, checkpoint 1, then exploration, with a checkpoint after every 5th exploration item (those checkpoints numbered from 2). The exploration section says "four kinds" and names three; the run rotates the three it names, in its order: bugs, speed on a weak machine, security and quality.

## T1 — a run that used a test hook is never ranked

**D2 — Acceptance criteria (derived).** (a) Any URL test hook in effect at a run's start (`seed`, `speed`, `boss`, `fps`, `crowd`, `elite`, `fusion`, `pickups`: every field `parseTestHooks` reads; no other Survival hook exists in `app/`) makes the run unrankable: no leaderboard form, no `startSurvivalRun` call. (b) The results say why in one line, naming the hooks. (c) The hooks behave as before. (d) A unit test shows a run with a hook marked unrankable and one without rankable. (e) An e2e test shows a seeded run's results with no leaderboard entry.

**D3 — "In effect", not "present".** A hook the URL names but cannot use (`?seed=0`, `?speed=1`, `?fps=0`) already "reads as no hook at all" (test-hooks.ts), so it does not count against the run either. Only a hook that changes something blocks ranking. `activeTestHooks` reuses `parseTestHooks`, so the bounds cannot drift apart. A unit test checks that it can name every field of `TestHooks`, so a hook added later without a name there fails.

**D4 — The seed and the frame counter now count too.** Before this task they were exempt, on the grounds that "a seed and the frame counter do not change the game". The plan names `?seed` and `?fps`. A seed lets a run be replayed until it is known, and is the easiest of them to share. The existing signed-out and signed-in leaderboard e2e tests used `?seed=7` only for repeatability, so they now run unseeded (they give up after 1.5 s, which no seed affects).

**D5 — The `survival` browser group now depends on the login setup.** The new test uses the demo user's session. `survival` was not in `LOGGED_IN` in `playwright.config.ts`, so a targeted run (`E2E_NO_CAT_DEPS=1`) reused whatever `playwright/.auth/demo-user.json` an earlier run left, signed with that run's throwaway `AUTH_SECRET`. That showed in this task as a `JWTSessionError` and a test that passed signed out. In a full run it worked only because `cat-attacks` (which depends on `setup`) ran first. The new test also opens `/dashboard` first and expects to stay there, so it cannot pass signed out. Changing `playwright.config.ts` makes the selector print `FULL` for this task's gate.

**D6 — What the server can and cannot check about a submitted run.** `recordSurvivalRun` (actions.ts) holds a run to: the signed-in player's own run, started by `startSurvivalRun`, finished once; a time no longer than its length, and no longer than the server's elapsed time since its start plus 2 s; at most 100 cats a second (+10); at most 60 finished runs an hour. It **cannot** see the URL, so it cannot tell whether a hook was used. The rule in this task is the client's, and stops an honest player posting a test run, not a cheater: Server Actions are public endpoints, so anyone signed in can call `startSurvivalRun`, wait, and call `recordSurvivalRun` with any time up to the real time elapsed and a plausible cat count, without playing. Nor can it check that the time was survived rather than idled. Stronger checks are proposed in Q3, not built (the plan says so).

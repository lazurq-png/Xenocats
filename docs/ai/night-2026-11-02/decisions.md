# Decisions — night-2026-11-02

Numbered non-obvious choices, with their reasons.

## T1 — Verify the database's certificate in production

- **D1** Acceptance criteria: (a) `app/lib/db.ts` connects with `ssl: 'verify-full'` when `VERCEL=1`, `'require'` otherwise; (b) the choice is a small function with its own unit test; (c) local and CI runs connect as before (`'require'`); (d) evidence that `'verify-full'` really checks the certificate.
- **D2** The function lives in its own module, `app/lib/db-ssl.ts`, not in `db.ts`, so a unit test can import it without creating the database client. It takes `env` as `trustedProxyHeader` (`sign-up-limit.ts`) does.
- **D3** For (d), an opt-in database test (`tests/unit/data.test.ts`, "TLS to the database") connects to the development or CI server, both self-signed, with the Vercel mode and expects a certificate error, and with the other mode expects `pg_stat_ssl.ssl = true`. It cannot show that Neon's certificate passes; see Q1.
- **D4** `scripts/db.mjs` (migrations, run by a human against Neon) still follows the URL's `sslmode` and so does not check the certificate either. That is outside the task's words (it names `app/lib/db.ts`); it is proposed in Q2 instead.

## T2 — One session check per request

- **D5** Acceptance criteria: (a) `app/lib/session.ts` reads the session through React `cache()`, so the overview's three components share one `auth()` (one `isCurrentSession` query) per request; (b) a test shows one call for several in one request, and a new call in the next request.
- **D6** Only `currentUserId()` goes through the cached `currentSession()`. The direct `auth()` calls in `actions.ts`, the export route, `cats/survival/page.tsx` and `leaderboard.tsx` each run once per request on their own page or action, so caching them saves nothing; they stay as they are.
- **D7** The test loads React's server build (the one Next gives Server Components; the client build's `cache` never memoises) and gives it a per-request cache through its dispatcher's `getCacheForType`, as React's server renderer does. That is a private React detail; if it changes, `cache` calls through and the test fails on its count rather than passing silently. A real Flight render in Vitest would need the `react-server` condition for the whole run.

## T3 — A login limit per client address

- **D8** Acceptance criteria: (a) each login attempt from a known client address is counted under that address, before the login name, keyed as the sign-up limit keys addresses (`clientKey`: HMAC of the address block with `AUTH_SECRET`); (b) past its limit the address is refused before any name is counted or any password compared; (c) the per-name lockout behaves as before; (d) `login_failures` rows whose lock and count have run out are pruned; (e) tests for each.
- **D9** Same table, own key prefix (`login-address:<hash>`), same counting statement (`claimAttempt`), so concurrent attempts are held to N as names are. A new column `last_attempt` (migration 0013) is needed: without a time, "a count that has expired" cannot be told from a live one.
- **D10** A success refunds its own attempt for the address (and the lock that attempt set, if it was the Nth) rather than clearing the address's count; clearing would let a client with an account of its own reset the count between guesses at other names.
- **D11** An address's count is forgotten after `lockMinutes` without an attempt (`forgetAfterMinutes`), so the failures of a shared address (an office, a NAT) do not pile up over weeks. A login name's count does not do this (criterion (c)): it gets `null`, which leaves its statement's outcome as before.
- **D12** Defaults: 20 failures per address (`LOGIN_ADDRESS_MAX_FAILURES`), locked for the same `LOGIN_LOCK_MINUTES`. Four times the per-name 5, so one household mistyping a few names is not locked; a guesser at one address gets 20 tries per 15 minutes across all names instead of 5 per name.
- **D13** No trusted proxy header (`trustedProxyHeader()` is null, as in development, CI and any deployment off Vercel without `TRUSTED_PROXY_HEADER`): every client's address is 'unknown', so the address count is skipped there, and only the login name is counted. The sign-up limit counts 'unknown' as one client instead; for logins that would let a few strangers' typos lock out every user. See Q3.
- **D14** Pruning runs on every login attempt that gets past the name's count, before the user lookup, so both a right and a wrong password pay for it (the time still tells nothing). It deletes rows whose lock has run out (the next attempt would start from 1 anyway, so no behaviour changes) and rows with no lock and no attempt for a day. The last is the one change a login name sees: fewer than N failures, then a day without an attempt, are forgotten.
- **D15** A locked address gets its own error code (`ADDRESS_LOCKED`) and message ("Too many failed logins from here."), since "for this account" would be wrong when the account is not locked.
- **D16** Two existing unit tests changed in what they match, not in what they assert: `credentials.test.ts` now looks for `DELETE FROM login_failures WHERE email` (the clear) instead of any `DELETE FROM login_failures` (which pruning also is), and `login-limit.test.ts` expects the count's parameters to be N, M and the quiet spell (null for a name).
- **D17** No browser test for the address limit: the test server has no trusted proxy, so every request is 'unknown' (D13) and the limit is off there. It is covered by unit tests (`credentials.test.ts`) and the real-database tests (`data.test.ts`); the existing `login-limit.spec.ts` covers the per-name limit in the browser.
- **D18** After the review: a quiet spell resets a count only when no lock is set (a lock set under a larger `LOGIN_LOCK_MINUTES` would otherwise let attempts through while it ran); pruning catches and logs its own errors, so housekeeping never fails a login; the README names `LOGIN_ADDRESS_MAX_FAILURES`.

## T7 — Plausibility checks on leaderboard runs

- **D32** Acceptance criteria: (a) `recordSurvivalRun` refuses a run claiming more cats sent home than the game could have sent home in its time and length; (b) the bound comes from the game's own numbers (its config), not a figure chosen here; (c) no run the game can play is refused; (d) tests at the limit (saved) and one past it (refused).
- **D33** The bound is every cat that can have come: a cat goes home once, so sent home ≤ came. `mostSentHome(ms, minutes)` in `arena.ts` adds each spawn source at its most, read from `ARENA_CONFIG` with the run length's changes (`runLengthConfig`): the arrivals at the rate `step` adds them with the horde empty (`wanted × arrivalShare + 1` a second, `wanted` taken at each second's end since it only grows, capped at `hardCap`), every swarm at its largest size, a xenocat's visit at the shortest gap, the Mega Cats due, the secret cat, and the Matriarch's kittens (none in a run the board takes: a timed run's time stops at its goal, and an endless one has no Matriarch). A step's slack (`stepMs`) is added to the time. A tighter bound (from the horde's real turnover) would need the simulation; this one cannot refuse a played run, whatever the weapons.
- **D34** Measured against a strong seeded run (both fusions at the highest level, a hero nothing wears down, real schedule): sent home 28 / 183 / 1,571 / 5,861 / 17,679 / 40,358 at 0:30 / 1:00 / 2:00 / 3:00 / 4:00 / 4:59, against bounds of 125 / 605 / 4,972 / 20,067 / 74,483 / 201,705. So the bound is 3–5× the strongest run measured: it catches a forgery of a large number, not a modest inflation (Q3 of 2026-10-17 called this option "catches only crude forgeries").
- **D35** The action reads the run's length (`SELECT run_minutes`) before the bound, then pins it in the `UPDATE` (`AND run_minutes = …`), so the check and the write are about the same run. One more query per finished run; a refused claim never reaches the `UPDATE`.
- **D36** Changed tests: `data.test.ts`'s "a run is saved once…" saved 100,000 cats in a minute with the comment "however many cats it sent home"; that is the behaviour the task removes, so it now refuses `most + 1` and saves `most`. `actions.test.ts`'s fake database answers the length lookup before the `UPDATE`.
- **D37** The arena's other configs (the test hooks' crowd, boss and fusion starts) are not bounded by this: their runs never reach the board (`leaderboard-entry.tsx` keeps hooked runs off it, D6 of 2026-10-17).
- **D38** After the review (Medium): a timed run reports its time stopped at the goal (`arena-view.tsx`, `Math.min(time, timeGoalMs)`), while its cats go on going home until the Matriarch reaches him, and a fast build can stay ahead of her for as long as he likes. A bound at the reported time would refuse such a run. The bound is therefore taken at the time since the run started on the server (`now() - started_at`, plus the 2 s start allowance), never less than the reported time: the game's clock cannot run ahead of the real one (pauses and level-ups stop it). A run left on its results screen only loosens it. Past the escalation's last point the arrivals are summed in one step, so a long elapsed time costs nothing. Tests: an arena run past its goal with a Matriarch that never moves, under the bound at the arena's clock and over `mostSentHome(goal)`; the action at the goal with more than `mostSentHome(goal)` but within the elapsed bound.
- **D39** After the review (Low): the refusal reads "… saved already, another run was started since, or it could not be checked." It still says nothing of the bound.
- **D40** Database tests keep their bound under the schema's 1,000,000 `sentHome` cap (a run started 6 minutes ago, an endless one 3 minutes ago), so the refusal they assert is the bound's and not the schema's.
- **D41** After the re-review (Low): the elapsed-time bound is for a timed run that reports its goal only (`run_minutes ≠ 0` and `timeMs ≥ run_minutes × 60 000`), the one case whose reported time is short of its clock. A run that ended before its goal, and an endless run, are held to the time they report, so waiting before saving loosens nothing.

## T9 — CI

- **D47** Acceptance criteria: (a) a `concurrency` group cancels a run superseded on the same branch or pull request; (b) the checks job runs `npx prettier --check .`; (c) the database-tests step fails when no test passed; (d) a pull request into `main` lists the `db/migrations/` files it adds in the job summary; (e) `.github/dependabot.yml`: npm weekly with minor and patch grouped, and GitHub Actions, both into `dev`.
- **D48** The group is the workflow and the pull request's number, else the ref, so a push to `dev` and a pull request from `dev` never cancel each other. A night run pushes `Nightrun` only once the previous task's poll has resolved (§2 step 4's gate), so it does not cancel its own runs; a CI-fix cycle's new push may cancel the run it replaces, which the poll reports as not observed, as it should.
- **D49** The guard reads Vitest's JSON report (`--reporter=json --outputFile.json=…`) through a small script, `scripts/ci-passed.mjs`, with a unit test (`tests/unit/ci-passed.test.ts`, in "Unit tests (dashboard)"), rather than grepping the console summary: the job runs in a container, where the default shell has no `pipefail`, so a `| tee` would hide Vitest's own exit code. Tried locally on real reports: a run with `DATABASE_TESTS=1` (52 passed) passes it; one without (all skipped, exit 0) fails it.
- **D50** The migrations job runs on every pull request into `main`, whether or not the `tested` job skips the tests (a release from `dev` is exactly when it matters). It lists files added (`--diff-filter=A`) between the base and the head (`BASE...HEAD`), writes them to the summary with the reminder to migrate Neon first, and annotates each with a warning; it fails nothing. Tried locally with `main`...`Nightrun`: it lists 0013 and 0014; with no new file, "None."
- **D51** The backlog's "CI's database tests can pass with every test skipped" entry is removed. `CLAUDE.md` §9 still says CI "has three jobs"; the new `migrations` job is a fourth, on pull requests into `main` only. The run does not edit `CLAUDE.md` for it (no task names that section); it is in the morning report's suggested rule changes.
- **D52** After the review (Low): the Formatting and Type check steps run whatever came before them (`if: ${{ !cancelled() }}`), as the unit-test groups do, so one failure does not hide the next check's result.
